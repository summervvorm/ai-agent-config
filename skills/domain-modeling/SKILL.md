# 领域建模（Domain Modeling）

在设计过程中主动建立并打磨项目的领域模型。这是一门 *主动* 的学科——挑战术语、构想边界场景、在想法刚成型时就把词汇表和决策写下来。（只是 *阅读* `CONTEXT.md` 取词不算本技能——那是任何技能都能做的一行习惯。本技能用于你在 *改变* 模型的时候，而不只是消费它。）

## 触发时机

当出现以下任一情况时触发本技能：

- 用户需要固定领域术语或统一语言（术语表 / glossary）。
- 用户需要记录一条架构决策（ADR）或维护 `CONTEXT.md` / domain 文档。
- 用户在设计讨论中使用模糊、过载或有歧义的词，需要被挑战或精炼。
- 需要把具体场景的压力测试应用到领域关系上，或核对代码与已陈述的行为是否一致。

## 文件结构

大多数仓库只有一个上下文（context）：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果仓库根目录存在 `CONTEXT-MAP.md`，说明有多个上下文。由该文件指引每个上下文存放在哪里：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按仓库现有约定来定位这些文件；不存在则按规范创建。文件要懒创建（lazy）——只有当你确实有内容要写时才创建。如果还没有 `CONTEXT.md`，在第一个术语被确定时创建它。如果还没有 `docs/adr/`，在第一条 ADR 需要时才创建。

## 工作流

### 对照词汇表挑战术语

当用户使用的术语与 `CONTEXT.md` 中已有的语言冲突时，立刻指出。"你的词汇表把 'cancellation' 定义为 X，但你好像指的是 Y——到底是哪个？"

### 精炼模糊语言

当用户使用模糊或过载的词时，提出一个精确的规范术语。"你说 'account'——你指的是 Customer 还是 User？这俩是不同概念。"

### 讨论具体场景

当领域关系被讨论时，用具体场景做压力测试。构想那些能试探边界、逼用户在概念交界处做精确判断的场景。

### 与代码交叉核对

当用户陈述某样东西如何工作时，核对代码是否一致。如果发现矛盾，就暴露出来："你的代码是取消整个 Order，但你刚才说部分取消是可能的——哪个才对？"

### 内联更新 CONTEXT.md

当一个术语被确定时，当场更新 `CONTEXT.md`。不要攒着一批再更新——要在发生时逐条捕获。格式见 [references/CONTEXT-FORMAT.md](references/CONTEXT-FORMAT.md)。

`CONTEXT.md` 应完全不含实现细节。不要把 `CONTEXT.md` 当规格、草稿本或实现决策的仓库。它只是词汇表，别的都不是。

### 谨慎地提供 ADR

只有以下三点同时成立，才提议创建 ADR：

1. **难以逆转**——事后改变想法的代价有意义
2. **没有上下文会很意外**——未来的读者会疑惑"他们为什么这么做？"
3. **真实权衡的结果**——确实存在可选的替代方案，而你出于具体原因选了其中一个

三者缺一，就跳过 ADR。格式见 [references/ADR-FORMAT.md](references/ADR-FORMAT.md)。

## 检查清单

- [ ] 术语已与 `CONTEXT.md` 词汇表核对，冲突当场指出
- [ ] 模糊/过载术语已精炼为精确规范术语
- [ ] 领域关系已通过具体边界场景压力测试
- [ ] 已核对代码与陈述行为是否一致，矛盾已暴露
- [ ] 已确定的术语已内联写入 `CONTEXT.md`（不含实现细节）
- [ ] 满足"难以逆转＋意外＋真实权衡"的决策已按 `references/ADR-FORMAT.md` 记录 ADR
