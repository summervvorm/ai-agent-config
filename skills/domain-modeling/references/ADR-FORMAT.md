# ADR 格式（ADR Format）

ADR 存放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

`docs/adr/` 目录要懒创建——只有第一条 ADR 需要时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句：背景是什么，我们决定了什么，为什么。}
```

就这样。一条 ADR 可以只是一个段落。价值在于记录 *做出了* 某个决策以及 *为什么*——而不是填满各个小节。

## 可选小节

只有确实增加价值时才包含这些。大多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策会被重新审视时有用
- **Considered Options**——只有当被否决的替代方案值得记住时
- **Consequences**——只有当非显而易见的下游影响需要被点名时

## 编号

扫描 `docs/adr/` 找出最高的现有编号，递增一。

## 何时提议 ADR

以下三点必须同时成立：

1. **难以逆转**——事后改变想法的代价有意义
2. **没有上下文会很意外**——未来的读者看代码会想"他们到底为什么这么做？"
3. **真实权衡的结果**——确实存在可选的替代方案，而你出于具体原因选了其中一个

如果某个决策容易逆转，就跳过——你反正会再改回去。如果它不令人意外，没人会问为什么。如果没有真正的替代方案，就没有什么可记录的，除了"我们做了显而易见的事"。

### 什么算 ADR

- **架构形态。** "我们用 monorepo。" "写模型是事件溯源的，读模型被投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带来锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都要记录——只记那些要花一个季度才能换掉的。
- **边界与范围决策。** "Customer 数据归 Customer 上下文所有；其他上下文只通过 ID 引用它。" 明确的"不"和"是"同样有价值。
- **对显而易见的路径的刻意偏离。** "我们用手写 SQL 而不是 ORM，因为 X。" 任何合理读者会假设相反做法的情况。这些能阻止下一位工程师"修好"某个刻意的决定。
- **代码里看不到的约束。** "由于合规要求我们不能用 AWS。" "由于合作伙伴 API 契约，响应时间必须低于 200ms。"
- **被否决但非显而易见的替代方案。** 如果你考虑过 GraphQL 却因为微妙的原因选了 REST，就记录下来——否则六个月后又会有人建议 GraphQL。
