# ADR Format

ADR（架构决策记录）放在 `docs/adr/`，使用递增编号：`0001-slug.md`、`0002-slug.md` 等。

懒建目录：需要第一个 ADR 时才创建 `docs/adr/`。

## 模板

```md
# {决策的短标题}

{1-3 句：上下文是什么、我们决定做什么、以及为什么。}
```

就这些。一条 ADR 可以只是一段话。价值在于记录*做了*这个决策以及*为什么*——而不是填满各个小节。

## 可选小节

仅在确实能增加价值时才包含，大多数 ADR 不需要它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策会被重访时有用
- **Considered Options**（被考虑的选项）——仅当值得记住被否掉的备选时
- **Consequences**（后果）——仅当需要点出非显而易见的后续影响时

## 编号

扫描 `docs/adr/`，取现有最大编号并加一。

## 什么时候值得写一条 ADR

以下三条必须同时成立：

1. **难推翻**——之后改变主意的代价是实在的
2. **脱离上下文会让人费解**——未来的读者看到代码会想"他们怎么会这么做？"
3. **确实是真正的权衡**——存在真正的备选，你因特定理由选了其中一个

如果决策容易推翻，跳过——你反正会改。如果不令人费解，没人会问为什么。如果没有真正的备选，除了"我们做了显而易见的事"之外无可记录。

## 什么算高价值决策

- **架构形态。**"我们用 monorepo。""写模型是事件溯源，读模型以投影方式落到 Postgres。"
- **上下文之间的集成模式。**"Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **有锁定效应的技术选型。**数据库、消息总线、认证供应商、部署目标。不是每个库——只指换起来要一个季度的那些。
- **边界与范围决策。**"Customer 数据归 Customer 上下文所有；其他上下文仅按 ID 引用。" 明确的"不做（no）"和"做（yes）"一样有价值。
- **刻意偏离显而易见路径。**"我们用手写 SQL 而非 ORM，因为 X。" 任何合理读者会默认相反的情况。这能阻止下一个工程师"修好"某个本是有意为之的东西。
- **代码里看不到的约束。**"因为合规要求我们不能用 AWS。""因为合作方 API 契约，响应时间必须低于 200ms。"
- **被否决的备选（其否决原因非显而易见时）。**如果你考虑过 GraphQL 却因微妙原因选 REST，请记录——否则六个月后还会有人再建议 GraphQL。
