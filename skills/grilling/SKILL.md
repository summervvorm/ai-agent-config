# Grilling（拷问式采访）

对用户的一个计划、决策或想法进行无休止的、一次一题的采访，沿着决策树逐层推进，直到双方对每一个决策都达成共同理解。你负责找出**事实**，用户负责拍板**决策**——把每个决策单独交给用户，等其确认后再继续。

本技能合并了五个相关源技能的精髓：基础采访循环（grilling）、可选的边采访边产出文档模式（grill-with-docs/domain-modeling）、批处理变体（batch-grill-me）、以及针对工作流规格的 loop 视角（loop-me）。

## 触发时机

当用户出现以下任一情况时触发本技能：

- 说"拷问我"、"grill 我"、"grill 这个想法/计划"、"压力测试一下"、"帮我把这个方案过一遍"
- 想厘清、打磨、压力测试一个计划、设计、决策或想法
- 想找到自己没注意到的假设或问题
- 想为想做的事（尤其是"生活/工作里的循环活动"）产出**工作流规格（workflow spec）**
- 希望边讨论边把决策和术语沉淀成 ADR 和 glossary 文档

用户一般需要主动控制本次采访。若用户只是想简单看一眼反馈而不是被逐步拷问，尊重其节奏。

## 工作流

一次采访的完整流程：

```
识别主题 → 明确目标模式 → 采访循环（一次一题 / 批处理轮次）
   ↓ 每答一问
记录决策 →（可选）边产文档：ADR / glossary / workflow spec
   ↓ 问题耗尽
检查共同理解 → 用户确认前不擅自执行
```

### 模式选择

开始前向用户确认（或用 `ask_user_question` 询问）采用哪种模式：

1. **基础模式**（默认）：一次一个问题，逐个遍历决策树。
2. **边采边写（with-docs）**：基础模式 + 采访过程中随手记录 ADR 和 glossary（见参考文献 `references/ADR-FORMAT.md`、`references/CONTEXT-FORMAT.md`）。单个决策敲定即落盘，不攒到最后。
3. **批处理模式（batch）**：把决策映射成一棵**设计树**，按轮次一次问整轮问题（见下文"批处理模式"）。
4. **loop 模式（loop-me）**：采访的唯一输出是**工作流规格**，见下文"loop 模式"。

## 步骤

### 1. 采访循环（核心纪律）

- **一次一题**：一次只问一个问题，等用户反馈后再继续。一次抛多个问题会让人感到困惑。
- **每个问题都附一个推荐答案**：不要只抛问题，给出你的建议和理由，帮用户更快做决定。
- **沿决策树分支下钻**：每解决一个决策，就走向依赖它的下一个决策，逐个厘清决策之间的依赖关系。
- **事实自己找，不要问用户**：如果某个*事实*能通过探索环境（文件系统、工具等）获得，就自己查（`read`/`grep`/`glob`/`pwsh`/`web_search`），而不是问用户。
- **决策属于用户**：每个*决策*都要单独交给用户，等其回答。
- **采访对象**：如果是要构建工作流或需要记录决策的采访，会涉及 ADR/glossary；这些直接在当前仓库按 `references/` 中的格式边问边写。

### 2. 提问工具（DSH）

提问使用 `ask_user_question` 工具。注意：

- 一次调用可传多个问题，但在**基础模式**中一次只问一个；把其余问题留到下一次调用。
- 为每个问题给一个稳定的 `id`，可在选项里附上你的推荐答案，便于用户一键确认。
- `add_answer`/用户答复返回后，据其继续。

### 3. 边采边写（with-docs 模式）

采用该模式时，把领域建模纪律合并进采访：

- **对照术语表挑战**：用户用了与现有 `references/` 中 glossary 冲突的词，当场指出："你这里说 X，但 glossary 里定义是 Y，到底是哪个？"
- **锐化模糊用词**：用户用含糊/多义词时，提议一个精确的规范术语。
- **用具体场景压力测试**：讨论边界关系时，编造能触及边界的场景逼用户把概念边界说清楚。
- **与代码交叉核对**：用户说"某事物如何工作"时，检查代码是否相符，发现矛盾就抛出来。
- **就地更新 glossary**：术语一经敲定，立刻写入 `CONTEXT.md`（或对应上下文文件），用 `references/CONTEXT-FORMAT.md` 的格式。不要攒批。
- **克制地写 ADR**：只有同时满足三条才写 ADR——①难推翻；②脱离上下文会让人费解；③确实经过了真正的权衡。用 `references/ADR-FORMAT.md` 的格式。大多决策不需要 ADR。

### 4. 批处理模式（batch）

把采访改造成**按轮次**进行：

- **设计树**：每个决策分支出依赖它的后续决策。
- **frontier（前沿）**：所有"前置条件已就绪、现在就能问"的决策。一轮就问**整条 frontier**：把每个问题编号，并附推荐答案。等用户答完这一轮再进下一轮。
- **逐轮重组**：用户回答会重塑设计树——已定决策把 frontier 向外推，解锁依赖它们的下一批问题。重算 frontier 再问下一轮。本轮某问题依赖另一个仍在本轮开放的答案时，它属于**更迟的轮次**，不属于本轮。
- **事实交给你**：frontier 里的问题若需要环境中的事实，就派 `subagent` 去查——能自己查到的东西绝不问用户。不要因此阻塞：正在探索的其实是未定的前置依赖，只有依赖它的下游问题才等 subagent 汇报，其余 frontier 现在照问。
- **结束条件**：frontier 为空——设计树每条分支都遍历过，没有决策被偷偷漏掉。用户确认共同理解前不执行。

### 5. loop 模式（loop-me）

当采访的唯一输出是**工作流规格**时采用。用 grilling 纪律（一次一题、每题附推荐答案），目标指向上文的词汇与目标。采访过程中创建、编辑、删除规格随结果演进。基础采访里商定的多数决策会直接写进工作流规格。

## loop 视角（配合 loop 模式使用）

- **loop（循环）**：用户生活中反复出现的模式——职业生涯、一周、一个早晨、一次重复的活动。把生活看作"循环套循环"，能看到日常活动有多可预测，而这正是值得**委托（delegating）**的原因。用这个视角找出值得规格化的循环，并主动提出用户没注意到的循环。
- **workflow（工作流）**：一个 loop 的规格、被实现成真实产物。你在某个 loop 上"跑"一个 workflow——loop 是它的运行实例。Workflows 存放在 "workflows/*.md"，是事实的源头。
- **定义完成（done）**：一个 workflow spec 完成后，实现者 agent 无需再问任何问题就能照做。grill 直到那里——只要还有一个问题，就什么都不算完成。

`workflows/*.md` 与 `NOTES.md` 的约定见"loop 模式工作区"。仓库若已有 AGENTS.md/CONTEXT.md 等约定文档，按既有约定执行；不存在需要时才创建。

## loop 词汇表（供工作流规格按需取用，绝非强制清单）

- **Trigger（触发器）**——触发每次运行的因素：**event（事件）**（新邮件、新 issue）或 **schedule（时间表）**（每天早晨）。事件触发通常更高效。
- **Checkpoint（检查点）**——人机协同点，在那里请用户核对或决策。有些 workflow 没有检查点、全自动运行；有些根本不用 AI。
- **Push right（右移）**——把检查点尽量向后推迟。在涉及人类之前做尽量多的活，让他们只被问一次、问得晚、且一切准备就绪。
- **Brief（简报）**——检查点呈现的内容：一个紧凑、可供决策的摘要——产出了什么、为什么、以及通向下层资产本身的链接——绝不是原始输出。用户读的是简报，不是草稿。审阅速度至关重要。

**不强加结构性要求**：一个 workflow 不需要 AI、不需要检查点、也不要时间表——除非采访表明需要。

## 完成与执行

- 采访完成的条件：决策树已遍历、问题耗尽、没有遗留的静默假设。
- **用户明确确认已达共同理解之前，不要动手实现**。理解一致后才开始执行。

## 检查清单

开始前、过程中、收尾时对照：

- [ ] 已与用户确认采用哪种模式（基础 / with-docs / batch / loop）
- [ ] 一次只问一个问题（基础模式）；每题都附推荐答案
- [ ] 派生问题不越级提前问；依赖未定的问题留到后续回合
- [ ] 能自己查的事实未问用户；用 read/grep/glob/pwsh/web_search 自己查
- [ ] （batch）frontier 判断正确，一轮问整条前沿，每问编号
- [ ] （batch）派 subagent 查环境事实且不阻塞其余 frontier
- [ ] （with-docs）术语敲定即写 glossary；决策满足三条才写 ADR
- [ ] （loop）判断哪些 loop 值得委托；workflow spec 完成度 = 实现者可零问题照做
- [ ] 用户确认共同理解前未动手执行

## 模板

### 单题问题（基础模式，一次一个）

```
「{当前决策点}」我的推荐是 {推荐答案}。
理由：{1-2 句}。你的选择是？
```

### 一轮问题（批处理模式，可选 after/batch）

```
本轮 frontier：
1. {决策 A}——推荐：{…}
2. {决策 B}——推荐：{…}
...
请逐条回答；有两题依赖彼此答案的，我放到下一轮。
```

### 术语敲定（with-docs 模式，就地写入 CONTEXT.md）

```
「{模糊词}」→ 定为「{规范术语}」：{一句定义}。
避免使用：{同义词}
```

### 工作流规格骨架（loop 模式）

```
# {工作流名}
- Trigger: event | schedule（附说明）
- Checkpoint: 有/无（在哪个点、问什么）
- Push right: 检查点放在最多活已干完的最后
- Brief: 检查点展示什么摘要
- 实现者无需追问即可照做的完整步骤
```
