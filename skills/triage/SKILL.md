# Triage（issue 分诊）

把仓库内的 issue 推进一套小的分诊状态机。本技能操作**本地文件**（`.scratch/triage/` 下的 issue 文件 + 状态标注），不依赖任何在线 issue tracker 或 `gh` 命令。

如果本仓库把外部 PR 视作请求面（按仓库约定判断），分诊同样覆盖它们：**一个 PR 就是带代码的 issue**——相同的分类、相同的状态、同一台状态机，只有下面标注"for a PR"的几处差异。把裸的 `#42` 解析为 issue 或 PR 时，按仓库的本地文件约定处理。

分诊期间，写入 issue 文件或发布到外部渠道的每条评论/说明**都必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 本地文件模式（替代在线 issue tracker）

没有内置 issue 跟踪器。issue 都在仓库的 `.scratch/triage/` 目录下落地为 markdown 文件：

```
.scratch/triage/
├── issues/<id>.md           # 每个 issue / PR 一个文件
└── out-of-scope/<concept>.md  # 被拒绝的 enhancement 知识库
```

每个 issue 文件带一个 frontmatter 状态标注（`category` + `state`），正文为问题描述、讨论与分诊记录：

```markdown
---
id: 42
category: bug          # bug | enhancement
state: needs-triage    # needs-triage | needs-info | ready-for-agent | ready-for-human | wontfix
---
# 标题

问题正文与后续评论…

## Triage Notes
（若已分诊，记录"已确认"与"仍需信息"）
```

- 列目录/筛选用 `pwsh`（如 `Get-ChildItem -Recurse .scratch/triage`），或直接 `read` / `glob` 单个文件。
- 改状态：用 `edit` 更新该文件的 frontmatter `category` / `state` 字段；改 `state` 为 `wontfix` 及其它需关闭的场景，可在文件末尾补充关闭说明。
- 文档可稍后由人工发布到真实 issue tracker；不要假设 `gh` 可用。

## 触发时机

- "Show me anything that needs my attention" / "看看哪些 issue 需要关注"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?" / "有哪些可以交给 agent"
- 任何要"先分诊、后处理/待办排队"的请求

## 角色（category 与 state）

两个**分类**角色：

- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等报告方补充信息
- `ready-for-agent` — 已完全明确，可交给 AFK agent
- `ready-for-human` — 需要人工实现
- `wontfix` — 不会被处理

对 PR，同一批状态对照附带的代码来读：`ready-for-agent` 表示已挂上 brief、agent 应在该 diff 上做下一步；`ready-for-human` 表示已就绪、等人合并。

每个被分诊的 issue 都应恰好带上一个 category 角色 + 一个 state 角色。若 state 角色冲突，先标记出来，并在做任何其它事之前询问维护者。

这是规范化的角色名——本地文件中实际的 category/state 取值应与之保持一致。若发现本仓库存在各自的命名约定（比如某个既有 frontmatter 字段），按现有约定来；否则按本技能统一。

**状态转移**：一个未标注的 issue 通常先到 `needs-triage`；随后移向 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告方回复后回到 `needs-triage`。维护者随时可以覆盖——标记看起来异常的转移，先询问再做。

## 工作流

### 展示需关注的内容

读取 `.scratch/triage/` 下的 issue 文件，按新旧顺序（最旧在前）呈现三桶：

1. **未标注** — 从未分诊过。
2. **`needs-triage`** — 评估中。
3. **`needs-info` 且上次分诊记录后有报告方活动** — 需重新评估。

当 PR 在范围内时，把外部 PR 纳入这些桶，并在每行标注 `[PR]` 或 `[issue]`。发现层面只呈现*外部* PR（按仓库约定判定谁算外部）——协作者进行中的 PR 不是分诊工作。此过滤仅限发现层面；被明确点名的一个 PR 无论作者是谁都照常分诊。

给出每桶的数量和每条一项的一行摘要，让维护者挑要处理哪个。

### 分诊单个 issue 或 PR

1. **收集上下文。** 通读整个 issue / PR 文件（正文、评论、category/state、作者、日期；对 PR 还要有 diff）。解析过往的分诊记录，别再问已解决过的问题。用仓库的领域词汇/约定探索代码库，尽量尊重该区域已记录的决策。对代码库跑两项检查：(a) **冗余性** — 按领域概念（而非请求的措辞）搜索该行为是否已存在实现，并报告你在哪里查过。若已存在，就是"已实现"的 `wontfix`（第 5 步）。(b) **先前拒绝** — 读 `.scratch/triage/out-of-scope/*.md`，暴露其中任何与本请求相似的概念。

2. **推荐。** 把你的 category 与 state 建议连同理由告诉维护者，附上与请求相关的简要代码库摘要——包括是否已实现。等指示。

3. **验证主张。** 在 grilling 之前，先确认主张成立。对 bug，按报告方的复现步骤复现。对 PR，确认 diff 确实做了它所声称的事——检出它、跑相关测试或命令。报告发生了什么：已确认（带代码路径）、失败、或信息不足（这是强烈的 `needs-info` 信号）。被确认的验证能让 agent brief 强得多。

4. **Grill（如需要）。** 若请求需要打磨成型，运行 `grilling` 与 `domain-modeling` 两个技能一起——一次一个问题地把它拷问成型，厘清领域术语；决策落地的同时更新领域的共识文档/记录。

5. **应用结果：**
   - `ready-for-agent` — 附加 agent brief（见 [references/AGENT-BRIEF.md](references/AGENT-BRIEF.md)）。
   - `ready-for-human` — 结构与 agent brief 相同，但注明为何不可委派（判断空间、外部访问、设计决策、手工测试）。
   - `needs-info` — 附加分诊记录（模板见下）。
   - `wontfix` — 标注状态并关闭，附注取决于**原因**：
     - **已实现** — 该改动已存在于代码库。指出它在哪里；**不要**写到 `.scratch/triage/out-of-scope/`（那个知识库只放*被拒绝*的请求，不放已做成的功能）。
     - **被拒绝（bug）** — 礼貌说明后关闭。
     - **被拒绝（enhancement）** — 写入 `.scratch/triage/out-of-scope/`，在关闭说明里链接到它后关闭（见 [references/OUT-OF-SCOPE.md](references/OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用该角色。可有可无地补一条评论，若有部分进展。

### 快速状态覆盖

若维护者说"move #42 to ready-for-agent"，直接信任并应用该角色。先确认你将做的事（角色变更、评论、关闭），然后行动。跳过 grilling。若要在没有 grilling 会话的情况下移到 `ready-for-agent`，询问是否想先写 agent brief。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把 grilling 期间已解决的一切都记到 "established so far"，以免工作丢失。问题必须具体、可行动，而不是"请提供更多信息"。

## 恢复上一次会话

如果 issue 或 PR 上已有分诊记录，先读它们，检查报告方是否已回答任何遗留问题，并在继续前呈现更新后的图景。不要重复问已解决的问题。

## 检查清单

- [ ] 每条分诊评论都以 AI 免责声明开头
- [ ] 每个 issue 恰好带一个 `category` + 一个 `state`
- [ ] `ready-for-agent` 有完整 agent brief（含可验证验收标准）
- [ ] `needs-info` 的问题具体可行动
- [ ] 被拒绝的 enhancement（非 bug、非已实现）写入了 `.scratch/triage/out-of-scope/`
- [ ] 已实现的 `wontfix` 指向代码位置，且不写入 out-of-scope
- [ ] 未重复问已解决过的问题
