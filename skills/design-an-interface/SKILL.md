# 设计一个接口（Design an Interface）

源于《A Philosophy of Software Design》中的 "Design It Twice"（设计它两遍）：你的第一个想法很可能不是最好的。先并行生成多个**截然不同**的设计，再逐一对比，最后综合。

## 触发时机

- 用户想设计一个新的 API / 模块接口，希望探索多种接口选项。
- 用户想比较某个模块的不同形状（面朝调用方的切片方式）。
- 用户提到 "design it twice"、"多出几版再对比"、"设计几个方案"。

## 工作流

### 1. 收集需求（Gather Requirements）

设计之前先弄清：

- [ ] 这个模块解决什么问题？
- [ ] 调用方是谁？（其他模块、外部用户、测试）
- [ ] 关键操作有哪些？
- [ ] 有什么约束？（性能、兼容性、现有模式）
- [ ] 哪些应留在内部被隐藏，哪些要对外暴露？

可问：*"这个模块需要做什么？谁会用？"* 需要澄清时用 `ask_user_question` 一次问多个问题。

### 2. 生成设计（并行子代理）

用 `subagent` 工具同时（后台）生成 3 个以上设计。每个子代理必须产出一个**截然不同**的方案。子代理没有本会话上下文，prompt 必须自包含——把模块描述、需求与约束完整写进每个 prompt。

并行启动：在同一条消息里发起多个 `subagent` 调用（默认后台运行）。若当前步骤依赖某个子代理结果才能继续，可对该代理用 `run_in_background: false`。

每个子代理的 prompt 模板：

```
为一个模块设计接口：[模块描述]

需求：[收集到的需求]

本方案约束：[给每个子代理分配一个不同的约束]
- 子代理 1："把方法数量压到最少——最多 1-3 个方法"
- 子代理 2："最大化灵活性——尽量覆盖多种使用场景"
- 子代理 3："为最常见的使用场景做最优化"
- 子代理 4："借鉴 [某个具体范式/库] 的思路"

输出格式：
1. 接口签名（类型 / 方法）
2. 用法示例（调用方如何使用）
3. 该设计在内部隐藏了什么
4. 该方案的权衡取舍
```

### 3. 呈现设计

逐个展示每个设计，包含：

1. **接口签名**（Interface signature）— 类型、方法、参数。
2. **用法示例**——调用方在实战中如何用。
3. **隐藏了什么**——被留在内部的复杂度。

按顺序依次呈现，让用户先消化各自方案，再进入对比。

### 4. 对比设计

展示全部设计后，围绕以下维度对比：

- **接口简单性**：方法更少、参数更简单。
- **通用 vs 专用**：灵活性与专注度的取舍。
- **实现效率**：该形状是否允许高效的内部实现？
- **深度**：小接口隐藏大量复杂度 = 深模块（好）；大接口配薄实现 = 浅模块（应避免）。
- **正确使用的难易** vs **误用的难易**。

用散文讨论权衡，不要用表格。重点标出各设计分歧最大的地方。

### 5. 综合（Synthesize）

往往最优设计是多个选项洞见的融合。问用户：

- "哪个设计最贴合你的主要使用场景？"
- "有没有其他设计中的元素值得吸收？"

## 评估标准

**接口简单性**：方法更少、参数更简单 = 更易学习、更易正确使用。

**通用性**：无需改动即可应对未来使用场景。但要警惕过度泛化。

**实现效率**：接口形状是否允许高效实现？还是会迫使内部写得别扭？

**深度**：小接口隐藏大量复杂度 = 深模块（好）；大接口配薄实现 = 浅模块（避免）。

## 反模式（Anti-Patterns）

- 不要让子代理产出相近的设计——强制"截然不同"。
- 不要跳过对比——价值就在反差里。
- 不要动手实现——这纯粹聚焦接口形状。
- 不要依据实现的工作量来评判设计。
