# Prototype

原型是**用来回答某个问题的可丢弃代码**。问题本身决定了原型的形状。

## 触发时机

- 用户想 sanity-check（验证）某个状态模型或逻辑是否合理。
- 用户想探索某个 UI 应该长什么样、想在看多个布局方案后做决定。
- 用户在真正写实现之前，想"按按钮看过状态变化"或"翻看几个界面变体"。
- 用户明确提到"原型""prototype""先做个东西看看"。

如果问题本质是逻辑/状态而非外观，走 Logic 分支；如果问题本质是外观而非逻辑，走 UI 分支。

## 选择分支

先从用户的话、上下文代码里判断要回答的是哪个问题；若拿不准且用户在线可以问，就问一下：

- **"这个逻辑 / 状态模型感觉对吗？"** → `references/LOGIC.md`。做一个极小的交互式终端应用，把状态机推着跑过那些在纸上很难想清楚的用例。
- **"这个界面应该长什么样？"** → `references/UI.md`。在同一个路由上生成几个差异极大的 UI 变体，通过 URL 的 `?variant=` 参数和底部悬浮条来回切换。

两个分支产出的东西差别很大——选错分支会浪费整个原型。如果问题真模糊且联系不上用户，就默认选择与现有代码更贴合的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两者都适用的规则

1. **从第一天起就可丢弃，并明确标注。** 把原型代码放在它真正会被用到的地方附近（要为其做原型的模块或页面旁边），上下文一目了然——但命名要让随手一读的人看出这是原型而非生产代码。对一次性 UI 路由，沿用项目已有的路由约定，不要发明新的顶层结构。
2. **一条命令即可运行。** 用项目现有的任务运行器支持的形态——`pnpm <名称>`、`python <路径>`、`bun <路径>` 等。让用户不用思考就能启动。
3. **默认不做持久化。** 状态只存在内存里。持久化是原型要去_验证_的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，用 scratch 库或本地文件，并起一个清晰的 "PROTOTYPE — wipe me" 名字。
4. **跳过打磨。** 不写测试，错误处理做到"可运行"即可，不做抽象。目的是快速学到东西。
5. **把状态亮出来。** 每次动作之后（逻辑）或每个变体切换时（UI），打印或渲染完整的相关状态，让用户看得见发生了什么变化。
6. **完成后把它留存。** 把验证过的决定落进真实代码，然后把原型本身作为**一手资料**留存：提交到 main 之外的一次性分支，并在实现 issue 上留下指向该分支的上下文指引。答案也要留下来——结论以及它所解决的那个问题，记在 issue 或一次 commit 里。main 分支只保留验证过的决定。

> 说明：DSH 没有内置 issue 跟踪器。涉及"在 issue 上记录答案 / 上下文指引"时，改为按仓库现有约定写本地 markdown 文件，例如 `.scratch/<feature>/` 下，并注明后续可人工发布到 issue 跟踪系统。
