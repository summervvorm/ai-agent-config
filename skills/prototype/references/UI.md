# UI 原型

在同一个路由上生成**几个差异极大的 UI 变体**，通过底部悬浮条切换。用户在浏览器里来回翻，选一个（或从各取所需偷一点),然后把其余的扔掉。

如果问题关于逻辑/状态而非界面长得什么样——那走错分支了。用 `references/LOGIC.md`。

## 什么时候这是正确的形状

- "这个页面应该长什么样？"
- "提交之前我想看看这个 dashboard 的几个方案。"
- "给设置页面换种不同的布局试试。"
- 任何用户本来会在脑子里花一天时间从三个模糊的 mockup 里做选择的时刻。

## 两个子形状——强烈优先选择子形状 A

UI 原型在**贴近应用的其余部分**时更容易评判——真实 header、真实侧栏、真实数据、真实密度。单独一个一次性路由是真空：每个变体单独看都好看。只要有一个说得过去的现有页面能承载这些变体，就默认走子形状 A。只有当你发现这个原型确实没有就近的归属时，才考虑子形状 B。

### 子形状 A——对现有页面的调整（首选）

路由已经存在。变体渲染在**同一个路由**上，由 `?variant=` URL 搜索参数门控。现有的数据拉取、参数、鉴权全部保留——只有渲染部分切换。这是默认选项，除非有明确理由不这么做。

如果原型是为了某个还没有页面、但*天然该住进一个页面里*的东西（dashboard 的新区块、设置界面上的新卡片、现有流程里的新步骤）——这仍然是子形状 A。把变体挂载进宿主页面里。

### 子形状 B——新页面（最后手段）

只有被原型化的事物确实没有可住的现有页面时才用它——例如一个全新的顶层界面，或一个无法嵌入任何合理位置的流程。

按项目已有的路由约定创建一个**一次性路由**——不要发明新的顶层结构。命名要看起来明显是原型（例如路径或文件名里带上 `prototype` 这个词）。同样的 `?variant=` 模式。

在敲定子形状 B 之前做个 sanity-check：真的没有能嵌入的现有页面吗？空的空的路由会藏住那些有内容的页面才会暴露出来的设计问题。

两种子形状下底部悬浮条都是一样的。

## 流程

### 1. 写明问题并定 N 值

默认**3 个变体**。超过 5 就不再是"差异极大"而是噪音了——封顶。

用一行把计划写在原型的所在地或文件顶部注释里：

> "设置页面的三个变体，通过 `?variant=` 切换，放在现有 `/settings` 路由上。"

用户无论在场回呛还是不在场，这行文字都成立。

### 2. 生成差异极大的变体

起草每个变体。让每一个都守住：

- 页面的用途、它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、plain CSS，随项目）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构性不同**——不同的布局、不同的信息层级、不同的主操作区(primary affordance)，而不是只换颜色。三个微调过的卡片网格不是 UI 原型，那是墙纸。如果两个草稿太像，就重做其中一个，并加上明确的"不要用卡片网格"的指引。

### 3. 把它们接起来

在路由上创建一个切换器组件：

```tsx
// 伪代码——请按项目框架适配
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形状 A（现有页面）：把现有数据拉取都放在切换器之上；按变体不同切换的只有渲染子树。

子形状 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

一个固定定位在屏幕底部居中的小横条，三样东西：

- **左箭头**——切到上一个变体（可回绕）。
- **变体标签**——显示当前变体的 key，如果变体导出 name 也显示。例如 `B — Sidebar layout`。
- **右箭头**——向后切（可回绕）。

行为：

- 点箭头更新 URL 搜索参数（用框架的路由器——Next 用 `router.replace`，React Router 用 `navigate` 等），让变体可分享、刷新后稳定。
- 键盘：`←` 和 `→` 也能循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 视觉上与页面区分明显（例如高对比度的胶囊、细微阴影），让人一眼看出它不是被评估的设计的一部分。
- 生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价判断门控，防止一次意外的原型合并把横条发给用户。

把切换器放进一个共享组件里，让两个子形状都能复用。放在项目里共享 UI 所在的位置。

### 5. 交出去

交出 URL（以及 `?variant=` 的 key）。用户什么时候有空就什么时候翻。最有价值的反馈通常是**"我想要 B 的 header 配 C 的 sidebar"**——那才是他们真正想要的设计。

### 6. 留存答案并清理

一旦某个变体胜出，先留存答案——哪个变体、为什么——再按主 SKILL 描述的方式留存原型。（DSH 无内置 issue 跟踪器：涉及"记在 issue"的部分改为按仓库约定写本地 markdown 文件，如 `.scratch/<feature>/`，注明后续可人工发布。）把胜者折进真实代码，其余移到一次性分支，而不是进 main：

- **子形状 A**——把胜者折进现有页面；把落选变体和切换器从 main 里去掉。
- **子形状 B**——把胜出的变体提升为真实路由；把一次性路由和切换器从 main 里去掉。

完整的变体集合是一手资料，所以它落到一次性分支而不是回收站——留在 main 分支里的变体组件和切换器很快就会腐坏并误导下一位读者。

## 反模式

- **只差颜色或文案的变体。** 那是微调，不是原型。真正的变体在结构上分岐。
- **变体之间共享太多代码。** 共享一个 `<Header>` 可以；共享一个 `<Layout>` 就失去意义了。每个变体都应该能自由扔掉布局。
- **把变体接到真实写操作上。** 只读原型没问题。如果某个变体需要变更，让指向一个 stub——问题是"这应该长什么样"，不是"后端好不好使"。
- **把原型直接提升为生产代码。** 变体代码是按原型约束写的（无测试、最小错误处理）。折进真实代码时要重新写清楚。
