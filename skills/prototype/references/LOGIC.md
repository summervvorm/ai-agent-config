# Logic 原型

一个极小的交互式终端应用，让用户亲手驱动状态模型。当问题是关于**业务逻辑、状态迁移或数据形状**时使用——这类东西在纸上看着合理，只有推着它跑过真实用例才会觉得不对劲。

## 什么时候这是正确的形状

- "我不确定这个状态机能不能处理『X 然后 Y』这种边界情况。"
- "这个数据模型到底能不能让我表达『……』这种情况？"
- "我想在动手写之前先感受一下这个 API 应该长什么样。"
- 任何用户想**按按钮、看状态变化**的场景。

如果问题是"界面应该长什么样"——那走错分支了。用 `references/UI.md`。

## 流程

### 1. 写明问题

动手写代码之前，先写下要原型化的状态模型以及要回答的问题。一段话即可，放在原型的 README 或文件顶部注释里。答错问题的逻辑原型纯粹是浪费——把问题显式写出来，这样无论用户此刻在看着、还是离开后(AFK)回来检查，都能核对。

### 2. 选语言

用宿主项目所用的语言。如果项目没有明显的运行时（例如纯文档仓库），就问一下。

尽量贴合项目现有的工具约定——不要为了原型单独引入新的包管理器或运行时。

### 3. 把逻辑隔离成可移植的模块

把真正回答问题的逻辑放在一个小的、纯的接口后面，以后可以直接把它提出来扔进真实代码库。周围的 TUI 是一次性可丢弃的；逻辑模块不该是。

形状取决于问题：

- **纯 reducer**——`(state, action) => state`。适合动作是离散事件、状态是单一值的场景。
- **状态机**——显式状态与迁移。当"当前哪些动作本来就不合法"本身就是问题的一部分时适用。
- **一组基于普通数据类型的纯函数**。适合没有隐式当前状态、只有变换的场景。
- **带清晰方法面的类或模块**，当逻辑确实持有持续的内部状态时。

选择最能回答当前问题的形状，*而不是*最方便接到 TUI 的那个。保持纯净：无 I/O、无终端代码、不用 `console.log` 控制流程。TUI 导入它、调用它；不反向流动。

这正是让原型在它自己的生命周期之外仍然有用的原因：问题答完之后，验证过的 reducer / 机器 / 函数集可以被独立提进真实模块。

### 4. 做一个最小的、把状态暴露出来的 TUI

做成**轻量 TUI**：每次 tick 都清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价写法）并重绘整帧。用户永远应该看到一个稳定的视图，而不是不断增长的滚动回放。

每帧两部分，按此顺序：

1. **当前状态**，格式化输出、便于 diff（每个字段一行，或格式化 JSON）。字段名或区块标题用**粗体**，次要上下文（时间戳、ID、派生值）用**暗淡(dim)**。原生 ANSI 转义码即可——`\x1b[1m` 粗体、`\x1b[2m` 暗淡、`\x1b[0m` 重置。除非项目里已有样式库，否则不必引入。

2. **键盘快捷键**，列在底部：`[a] add user  [d] delete user  [t] tick clock  [q] quit`。键名加粗、描述用暗淡，或反过来——读起来清晰即可。

行为：

1. **初始化状态**——一个内存中的对象/结构体。开始时渲染第一帧。
2. **逐次读取一个按键（或一行）**，分发给一个改变状态的 handler。
3. **每次动作后重绘整帧**——不要追加，要替换。
4. **循环直到退出。**

整帧应能容纳在一个屏幕内。

### 5. 让它一条命令可运行

在项目现有任务运行器里加一个脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户应该运行 `pnpm run <原型名>` 或等价命令——永远不需要记路径。

如果宿主项目没有任务运行器，就把命令放在原型 README 顶部。

### 6. 交出去

给用户运行命令。他们自己驱动它；有趣的时刻是他们说出"等等，这不应该可能发生"或"嗯，我还以为 X 会不一样"——那些就是_思路_里的 bug，而这正是全部意义所在。如果他们想加新动作，就加上。原型是会演化的。

### 7. 留存答案和原型

一旦原型回答了问题，先留存答案，再按主 SKILL 描述的方式留存原型。逻辑侧的具体映射：验证过的 reducer / 机器 / 函数集提进真实模块（作为已吸收的决定）；TUI 外壳跟着进到保留原型作一手资料的一次性分支。

> 留存出口说明：DSH 无内置 issue 跟踪器，涉及"在 issue 记录"的部分改为按仓库约定写本地 markdown 文件（如 `.scratch/<feature>/`），注明后续可人工发布。

## 反模式

- **不要加测试。** 需要测试的原型就不再是原型了。
- **不要接真实数据库。** 用内存 store，除非问题专门是关于持久化。
- **不要泛化。** 不要"万一我们以后想支持 X 呢"。一个原型只回答一个问题。
- **别把逻辑和 TUI 揉在一起。** 如果 reducer / 状态机里出现 `console.log`、提示或终端转义码，它就不再可移植了。让 TUI 保持成包在纯模块外的一层薄壳。
- **不要把 TUI 外壳交付到生产。** 外壳是为了人手工在终端驱动而优化的。它背后的逻辑模块才是值得保留的部分。
