# 实现功能（Implement）

根据 spec 或一组 tickets 实现用户所描述的工作。

## 触发时机

当出现以下场景时触发本技能：

- 用户给出规格（spec）或一组 tickets，要求"按此实现"。
- 用户要求把需求拆解成开发项并逐一完成。
- 用户说"实现这个功能""写这块逻辑""完成这个 ticket"。

## 工作流

1. 读取 spec 或 tickets，明确要实现的范围与验收标准；如有多个 ticket，建立 `todo_write` 任务清单逐项跟踪。
2. 优先在约定好的接缝（pre-agreed seams）处使用 **tdd** 技能测试先行开发。
3. 开发过程中**定期**做类型检查，**定期**单独运行单测文件。
4. 全部完成后，**跑一次全量测试套件**。
5. 用 **code-review** 技能复查本次工作。
6. 把工作提交到当前分支。

## 步骤

### 1. 理解范围
- 读 spec 或所有 tickets，明确每项做什么、产出什么、如何验收。
- 不确定时用 `ask_user_question` 向用户确认拆分与优先级。

### 2. 测试先行（tdd）
- 在可行的接缝处调用 **tdd** 技能：先写失败测试，再实现，再让测试通过。
- 遵循 tdd 技能给出的节奏与约定。

### 3. 定期校验
- **类型检查**：按项目现有约定定期运行（如 `npx tsc --noEmit`、`mvn compile`、`cargo check` 等，具体命令随语言/仓库而定），保持类型无错误。
- **单测**：改动涉及某个模块时，先单独运行对应的单测文件（如 `npx jest <file>`、`pytest <file>`、`go test ./<pkg>`），快速反馈。

### 4. 全量测试
- 全部实现完成后，运行一次完整测试套件，确保没有回归。

### 5. 代码复查
- 用 **code-review** 技能对本次改动做复查，按复查意见修正。

### 6. 提交
- 将工作提交到**当前分支**（使用 `pwsh` 的 git 命令完成 `add` / `commit`；不要创建新分支，除非用户明确要求）。

## 检查清单

- [ ] 已读取 spec / 所有 tickets，范围与验收标准明确
- [ ] 在可行接缝处使用了 tdd 技能
- [ ] 定期完成类型检查且无错误
- [ ] 定期运行相关单测文件且通过
- [ ] 结束时跑过全量测试套件且通过
- [ ] 用 code-review 技能复查并处理了意见
- [ ] 已提交到当前分支
