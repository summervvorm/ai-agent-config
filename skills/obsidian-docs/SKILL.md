# Obsidian 文档输出规范

本技能定义了所有技术文档的输出规范，确保文档统一输出到 Obsidian Vault 并符合 Obsidian 的最佳实践。

## 核心原则

1. **统一输出路径**：所有文档输出到 `C:\Users\<USER>\Documents\Obsidian Vault\文档\`。写入优先使用 mcp-obsidian 工具（`obsidian_write_note`/`obsidian_append_to_note`/`obsidian_patch_note`，路径用 vault 相对路径如 `文档/设计文档/xx.md`）；工具不可用时再直接写文件系统。
2. **聚合优先，按需拆分**：一个需求的文档**默认合并为一份聚合文档**（设计/数据模型/接口/流程/测试/上线以章节区分），只有模块级大需求才按类型拆分多份；**严禁为中小需求生成一堆碎片小文档**
3. **大类+子目录分类**：按文档类型建立一级目录，仅大需求建立二级子目录
4. **Obsidian 原生特性**：使用 `[[双向链接]]`、`#标签`、Callout 块等特性
5. **固定模板**：模板作为聚合文档内的**章节模板**使用（大需求拆分时才独立成文件），保证结构一致

## 目录结构规范

```

│   │   └── 排柜系统-需求池设计.md
│   └── 地区信息-设计文档.md   # 小需求直接放文件
├── 接口文档/                  # 本系统 RESTful API 接口文档
│   └── 地区表-sys_region-接口文档.md
├── 第三方平台接口文档/        # 第三方平台(领星/亚马逊/Wayfair/Mirakl等)接口说明
│   └── 领星-FBA库存明细-接口文档.md
├── ERD文档/                   # 实体关系图、数据模型、ODS/分层架构设计

│   └── 排柜系统/

> [!warning] 接口文档 vs 第三方平台接口文档
> `接口文档/` 收**本系统对外/对内的 RESTful API**（Controller 层）。
> `第三方平台接口文档/` 收**对接的第三方平台 OpenAPI 说明**（领星、亚马逊、Wayfair、Mirakl 等外部接口的字段/调用方式）。
> 二者性质不同，不可混放。

### 分类判断规则

| 文档内容 | 一级目录 | 文件命名格式 |
|----------|----------|-------------|
| **中小需求（默认）**：一个需求的设计+表+接口+流程+测试+上线 | `设计文档/` | `{需求名}.md`（**聚合文档**，章节区分） |
| 系统/模块/方案的整体设计思路、架构决策（大需求拆分时） | `设计文档/` | `{系统名}-{主题}-设计文档.md` |
| 本系统 RESTful API 接口定义、请求响应格式（大需求拆分时） | `接口文档/` | `{模块名}-接口文档.md` |
| 第三方平台 OpenAPI 说明、外部接口字段/调用方式 | `第三方平台接口文档/` | `{平台名}-{接口名}-接口文档.md` |
| 实体关系图、表关联、数据模型全景、ODS/分层架构、库存计算规则（大需求拆分时） | `ERD文档/` | `{系统名/需求名}-ERD{与...}.md` |
| 单表/多表 DDL、字段说明、索引设计（大需求拆分时） | `表设计文档/` | `{表名}-表设计.md` |
| 流程图、时序图、状态机图（Mermaid）（大需求拆分时） | `流程图文档/` | `{系统名}-{流程名}.md` |
| 功能测试计划、接口验证、联调测试用例、测试步骤与预期结果（大需求拆分或独立测试委托时） | `测试文档/` | `{系统名}-{模块}测试文档.md` |
| 需求迭代、改动点汇总、版本变更记录、合箱规则迭代 | `迭代文档/` | `{系统名}-{迭代主题}迭代.md` |
| 上线脚本、Nacos 配置、字典配置、其他配置（大需求拆分或独立交付时） | `上线文档/` | `{系统名}-{模块}-上线文档.md` |
| 环境配置、账号信息、操作手册、研发规范 | `其他文档/` | `{主题}.md` |

> [!warning] 聚合优先，拆分是例外
> 中小需求**必须**输出一份聚合文档（`设计文档/{需求名}.md`），用章节区分 设计/数据模型(DDL+ERD)/接口/流程/测试/上线，**禁止一个需求拆出 4-5 份碎片小文档**。只有命中下方拆分标准的模块级大需求才按类型拆分文件；拆分后每份文档仍只归属一个一级目录，且聚合主文档中的对应章节只留 `[[]]` 引用链接。**唯一例外**：第三方平台接口文档永远独立成文件（外部契约，不属于需求自身设计）。

### 拆分标准（仅模块级大需求）

同时满足以下**全部**条件才按类型拆分多份文档，否则一律聚合为一份：
- 该需求是独立的项目/模块级交付（如"排柜系统"、"对账模块"、"采购计划单一期"）
- 且文档总量预计超过 1000 行（聚合文档过大不便维护时）
- 或用户明确要求拆分

子目录命名：`{需求名称}/`，使用中文，简洁明了。拆分时各类型文档放入该子目录；聚合主文档（总体设计）保留在各章节内放 `[[]]` 链接指向拆分文档。

### 聚合文档章节结构（中小需求默认）

```markdown
# {需求名}
> [!info] 文档信息（创建时间/关联模块/分支）
## 一、背景与设计（方案/决策/状态机/流程图 Mermaid）
## 二、数据模型（ERD Mermaid + 各表 DDL + 字段说明）
## 三、接口定义（接口总览表 + 关键接口的入参出参与示例）
## 四、测试要点（核心用例与验证清单）
## 五、上线清单（DDL/配置/验证 checklist）
## 六、相关文档（[[]] 链接）
---
**标签**：#设计文档 #{需求名} ...
```
章节按需裁剪：纯 CRUD 小需求可省"测试要点"之外的章节；接口超过 10 个或 DDL 超过 3 张表时建议触发拆分评估。

## Obsidian 特性使用规范

### 1. 双向链接 `[[]]`

在文档中**主动链接**相关文档，建立知识图谱：

```markdown
## 相关文档
- 接口定义详见 [[地区表-sys_region-接口文档|地区表接口文档]]
- 数据库设计参考 [[sys_region-表设计|sys_region 表设计]]
- 整体架构见 [[畅泰云-架构设计|畅泰云架构设计]]
```

规则：
- **使用文件名（最短路径）**：`[[文件名]]` 或 `[[文件名|显示文本]]`，Obsidian 会自动按文件名解析，**不要用** `../` 相对路径（移动文件后相对路径会断链）
- 同名文件消歧：若 Vault 内有同名文件，用 `[[目录名/文件名]]` 消歧（如 `[[排柜系统/排柜系统-总体设计]]`）
- 可加别名：`[[文件名|显示文本]]`
- 每个文档**必须**包含"相关文档"章节，至少链接 1-2 个关联文档

### 2. 标签 `#标签`

每个文档末尾必须添加标签行，格式：

```markdown
---
**标签**：#设计文档 #排柜系统 #sys_region #接口文档
```

标签规则：
- 使用中文技术标签，具体明确
- 第一个标签为文档类型（如 `#设计文档` `#接口文档` `#ERD文档` `#测试文档`）
- 之后为系统/模块名、表名、技术关键词
- 标签数量：3-8 个

### 3. Callout 块

用于突出关键信息：

```markdown
> [!note] 设计要点
> 这里记录关键设计决策

> [!warning] 注意事项
> 这里记录需要注意的风险点

> [!tip] 最佳实践
> 这里记录推荐做法

> [!info] 版本信息
> - 创建时间：2026-06-05
> - 作者：AI 生成
> - 关联需求：排柜系统一期
```

### 4. Mermaid 图表

流程图、ERD、时序图等使用 Mermaid 语法：

```markdown
```mermaid
flowchart TD
    A[开始] --> B[处理]
    B --> C[结束]
```
```

> [!warning] Mermaid 11.x 兼容性规则（Obsidian 2025.1+ 已升级至 Mermaid 11.x）
> Obsidian 的 Markdown 预解析器会在 Mermaid 引擎渲染前，**先扫描双引号 `""` 内的纯文本**。以下模式会触发预解析器误判，导致 `Unsupported markdown: list` 错误，图表无法渲染：
>
> | ❌ 禁止写法 | ✅ 正确写法 | 原因 |
> |------------|------------|------|
> | `["1. 步骤一"]` | `["①步骤一"]` 或 `["1.步骤一"]` | `数字.空格` 被误判为有序列表 |
> | `["2. 步骤二"]` | `["②步骤二"]` 或 `["2.步骤二"]` | 同上 |
> | `["- [ ] 待办"]` | `["\[ ] 待办"]` 或 `["\- [ ] 待办"]` | `- [ ]` 被误判为任务列表 |
>
> **核心规则：Mermaid 双引号内，绝对不要写 `数字. `（数字+英文句号+空格），这是触发 `Unsupported markdown: list` 的唯一根源。**
>
> 推荐做法：
> - 序号用中文圈号 `①②③④⑤⑥`（最稳妥，无歧义）
> - 或写 `数字.内容`（无空格，如 `1.加载字典`）
> - 换行用 `<br>` 代替 `\n`（Mermaid 标准换行，兼容性更好）
> - `flowchart` 关键字可用 `graph` 替代（兼容低版本 Obsidian）
> - 节点文本中的 `/`、`_` 等字符在双引号内通常安全，无需转义

### 上线文档模板

> [!warning] 精简与 DDL 单一来源原则
> 上线文档**只收录执行清单**，不重复设计内容。
> **表结构变更直接维护进 `CREATE TABLE` 原始语句**（表设计章节/聚合文档数据模型章节始终保持最新全量 DDL），上线文档只引用"哪些表/字段是本次新增"，**禁止在上线文档堆砌 ALTER 追加语句**——CREATE TABLE 永远是可直接建库的最新状态，避免"先建旧表再打补丁"。

```markdown
# {系统名} - {模块}上线文档

> [!info] 文档信息
> - 创建时间：{YYYY-MM-DD}
> - 关联分支：{分支名}

## 一、SQL 清单

> 最新全量 DDL 见 [[{聚合文档名}#数据模型|数据模型章节]]（CREATE TABLE 已含本次全部字段变更）。
> 以下仅列**存量库**需执行的增量（新库直接按最新 CREATE TABLE 建）：

```sql

## 输出流程

1. **评估需求规模**：默认输出 1 份聚合文档（`设计文档/{需求名}.md`，章节区分）；仅命中拆分标准才建子目录拆多份
2. **判断归属目录**：聚合文档放 `设计文档/`；第三方平台接口文档独立放 `第三方平台接口文档/`
3. **确保目录存在**：如目录不存在，先创建
4. **使用章节模板**：按聚合文档章节结构填充，各章节内部参考对应类型的模板（接口/DDL/流程图等）
5. **添加 Obsidian 特性**：双向链接、标签（聚合文档打多类型标签）、Callout 块
6. **写入文件**：优先用 mcp-obsidian 工具（`obsidian_write_note`，target 用 vault 相对路径 `文档/{一级目录}/{文件名}.md`），MCP 不可用时再用完整绝对路径写文件系统

## 已有文档整理与聚合

当用户要求整理已有文档，或首次启用此技能时，按以下步骤执行：

1. 扫描 `C:\Users\<USER>\Documents\Obsidian Vault\文档\` 下的所有 `.md` 文件
2. **聚合**：同一需求下 3 份及以下的小文档（或单份低于 150 行的表设计/接口/流程小文档），合并为一份聚合文档（章节区分），合并后执行"删除/归档文档前安全检查"
3. **归类**：无法聚合的文档按类型移动到对应一级目录
4. **清理**：被新版本覆盖的过期文档、无引用且内容已失效的文档，列入候选删除清单
5. 更新文档间的双向链接引用（合并/删除后修复 `[[]]` 断链）

### 删除/归档文档前安全检查

**必须**在删除或归档任何文档前执行以下检查，防止误删导致知识图谱断链：

1. **引用检查**：在 Vault 内 grep 目标文件名，确认无其他文档用 `[[]]` 链接引用它。有引用的文档不可直接删除，须先更新引用方。
2. **取代检查**：确认目标文档的内容已被新文档完整覆盖（读取新旧文档头部/关键章节对比）。
3. **安全检查**：若文档含明文密钥/Token/密码，**优先删除**（无论引用状态），并通知用户轮换泄露的凭据。
4. **确认机制**：列出候选删除清单（含理由），向用户确认后方可执行删除。不可自行决定删除。
