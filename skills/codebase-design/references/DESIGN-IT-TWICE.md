# 设计两次（Design It Twice）

当用户想为某个已选定的加深候选对象探索备选接口时，使用这种并行子代理模式。基于 "Design It Twice"（Ousterhout）——你的第一个想法多半不是最好的。

假设已具备 [SKILL.md](../SKILL.md) 中的词汇——**module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 界定问题空间

在派出子代理之前，为选定的候选对象写一段面向用户的"问题空间"说明：

- 任何新接口都必须满足的约束
- 它将依赖的依赖，以及这些依赖属于哪一类（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的示意性代码草稿来锚定这些约束——不是提案，只是让约束具体化的一种方式

把它展示给用户，然后立即进入步骤 2。用户在子代理并行工作期间阅读与思考。

### 2. 派出子代理

用 `subagent` 工具**并行**派出 3 个以上子代理（默认后台运行，一次消息中同时启动它们）。每个子代理必须产出一个与其余**截然不同**的深模块接口设计。

为每个子代理准备一份独立的、包含文件路径、耦合细节、依赖类别（见 [DEEPENING.md](DEEPENING.md)）、以及 seam 后面是什么的技术简报。这份简报独立于步骤 1 中面向用户的问题空间说明。给每个代理一个不同的设计约束：

- Agent 1："把接口做到最小——力争最多 1–3 个入口点。让每个入口点的杠杆（leverage）最大化。"
- Agent 2："最大化灵活性——支持许多用例与扩展。"
- Agent 3："为最常见的调用方优化——让默认情形平凡到几乎不用操心。"
- Agent 4（如适用）："围绕 ports & adapters 来设计，处理跨 seam 依赖。"

简报中要同时包含 [SKILL.md](../SKILL.md) 的词汇与**项目域语言**（按仓库现有约定；如仓库有 CONTEXT/映射文档等，引用其词汇），以便每个子代理命名时与架构语言、项目领域语言一致。

每个子代理输出：

1. 接口（类型、方法、参数——外加不变量、顺序、错误模式）
2. 一个展示调用方如何使用它的用法示例
3. 实现藏在 seam 后面的是什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——哪里杠杆高、哪里薄

### 3. 呈现与比较

逐个顺序呈现各个设计，让用户逐一吸收，然后用文字比较它们。按 **depth**（接口处的杠杆）、**locality**（变更集中在何处）与 **seam 位置**进行对照。

比较之后，给出你自己的建议：你认为哪个设计最强、为什么。如果不同设计中的元素能很好地相互结合，提出一个混合方案。要有明确观点——用户要的是有力的判断，不是一份罗列菜单。
