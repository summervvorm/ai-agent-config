# 加深（Deepening）

如何安全地加深一个浅模块簇，给定其依赖。假设已具备 [SKILL.md](../SKILL.md) 中的词汇——**module**、**interface**、**seam**、**adapter**。

## 依赖分类

评估某个加深候选对象时，先对其依赖分类。类别决定加深后的模块如何跨其 seam 测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。总是可以加深——合并这些模块，直接通过新接口测试即可。不需要 adapter。

### 2. 本地可替换（Local-substitutable）

有本地测试替身的依赖（例如用 PGLite 代替 Postgres、用内存文件系统）。只要替身存在即可加深。加深后的模块用替身在测试套件中运行来测试。这条 seam 是内部的；模块外部接口处没有端口（port）。

### 3. 远程但自有（Ports & Adapters）

你自己跨网络边界（微服务、内部 API）的其它服务。在 seam 处定义一个**端口（port，即接口）**。深模块拥有逻辑；传输层作为 **adapter** 注入。测试用内存 adapter；生产用 HTTP/gRPC/队列 adapter。

推荐句式：*"在 seam 处定义一个端口，为生产实现一个 HTTP adapter、为测试实现一个内存 adapter，这样即使跨网络部署，逻辑仍集中在单个深模块里。"*

### 4. 真正外部（Mock）

你不控制的第三方服务（Stripe、Twilio 等）。加深后的模块把外部依赖作为注入的端口；测试提供一个 mock adapter。

## Seam 纪律

- **一个 adapter 意味着假设性的 seam；两个 adapter 意味着真实的 seam。** 除非至少两个 adapter 是合理的（通常是生产 + 测试），否则不要引入端口。单 adapter 的 seam 只是间接层。
- **内部 seam 与外部 seam。** 深模块可以同时有内部 seam（私有于实现、供其自身测试用）和位于接口处的外部 seam。不要仅仅因为测试用了内部 seam 就把它们通过接口暴露出去。

## 测试策略：替换，不要堆层（replace, don't layer）

- 一旦存在加深后模块接口处的测试，浅模块上的旧单元测试就变成浪费——删除它们。
- 在加深后模块的**接口处**写新测试。**接口就是测试面（the interface is the test surface）**。
- 测试断言接口处可观察的结果，而不是内部状态。
- 测试应当能经受内部重构——它们描述的是行为，不是实现。如果一个测试在实现改变时必须跟着改，那它就是在测到接口内部去了。
