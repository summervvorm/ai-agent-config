# QA 会话

运行一次交互式 QA 会话。用户用自然语言描述遇到的问题。你负责澄清情况、后台探索代码库获取上下文与领域语言，并为每个问题生成一份**持久、面向用户、使用项目领域语言**的 issue 记录。

## 触发时机

- 用户要报告 bug、做 QA、以对话方式提 issue。
- 用户提到 "QA session"、"提 issue"、"记录 bug"、"这是我遇到的问题" 等。
- 用户描述了一个可复现的异常行为，需要整理成结构化问题记录。

## 针对用户提出的每个问题

### 1. 倾听并轻量澄清

让用户用自己的话描述问题。最多问 **2-3 个简短澄清问题**，聚焦于：

- 预期是什么 vs 实际发生了什么（expected vs actual）。
- 复现步骤（如果不明显）。
- 是稳定复现还是偶发（consistent or intermittent）。

**不要过度采访。** 如果描述已经清楚到可以归档，就直接进入下一步。澄清提问使用 `ask_user_question` 工具，一次可同时问多个问题。

### 2. 后台探索代码库

在与用户交谈的同时，用 **`subagent` 工具**在后台启动一个探索型子代理，去理解相关区域。目的不是找修复方案，而是：

- 学习该区域使用的领域语言（检查仓库是否有 UBIQUITOUS_LANGUAGE.md / 领域语言文档）。
- 理解该功能本应做什么。
- 识别用户可见的行为边界（behavior boundary）。

这些上下文帮你写出更好的 issue——但 issue 本身**不应**引用具体文件、行号或内部实现细节。子代理没有本会话上下文，prompt 必须自包含；如非必须立即拿结果，保持后台运行，继续服务用户。

### 3. 判断范围：单个 issue 还是拆分？

归档前，判断这是一个 **单个 issue** 还是需要**拆分成多个**。

需要拆分的情况：

- 修复跨越多个相互独立的区域（例如 "表单校验错了 且 成功提示缺失 且 跳转坏了"）。
- 存在明显可分、可由不同人并行处理的关注点。
- 用户描述的内容有多个不同的失败模式或症状。

保留为单个 issue 的情况：

- 只有一个位置上的一个行为出错。
- 所有症状都由同一个根行为导致。

### 4. 归档 issue 记录

本技能不发布到在线 issue 跟踪器（DSH 无内置跟踪器），而是写入**本地 markdown 文件**，稍后可人工发布到 GitHub/GitLab 等。文件路径约定：`.scratch/qa/<NN>-<slug>.md`，其中 `<NN>` 是两位流水号（01、02…），`<slug>` 是简短英文标识。失败时不中断——把待发布说明与文件写入流程告诉用户。**不要先让用户审阅再归档——直接归档并给出文件路径。**

issue 必须**持久**——即使经过大的重构依然有意义。从用户视角书写。

#### 单个 issue 的模板

写入 `.scratch/qa/<NN>-<slug>.md`：

```
## What happened

[用平实的语言描述用户实际体验到的行为]

## What I expected

[描述预期的行为]

## Steps to reproduce

1. [具体、编号的步骤，开发者可以照做]
2. [使用代码库的领域术语，不要用内部模块名]
3. [包含相关输入、标志或配置]

## Additional context

[用户或代码库探索中得到的任何有助于框定该问题的额外观察——例如 "只在用 Docker 层时发生，文件系统层不会"——用领域语言描述，但不要引用文件]
```

#### 拆分成多个 issue 的模板

先创建跟踪问题（父 issue），再按依赖顺序创建各子 issue，以便引用真实编号。

每个子 issue 的模板：

```
## Parent issue

<父 issue 编号>（如果创建了跟踪问题）或 "Reported during QA session"

## What's wrong

[只描述这一个行为问题——只是这一片，不是整份报告]

## What I expected

[这一片的预期行为]

## Steps to reproduce

1. [仅针对这个 issue 的步骤]

## Blocked by

- <issue 编号>（如果这个 issue 必须等另一个解决了才能修）

或 "None — can start immediately"（无阻塞时）。

## Additional context

[任何与该片相关的额外观察]
```

拆分时：

- **宁要多个薄 issue，不要几个厚 issue** —— 每个都应可独立修复、独立验证。
- **如实标注阻塞关系** —— 如果 issue B 确实要等 issue A 修好才能测试，就说清楚；如果彼此独立，都标 "None — can start immediately"。
- **按依赖顺序创建**，以便在 "Blocked by" 里引用真实编号。
- **最大化并行度** —— 目标是让多个人（或代理）能同时拿走不同 issue。

#### 所有 issue 正文的通用规则

- **不写文件路径或行号** —— 这些会过时。
- **使用项目的领域语言**（如存在 UBIQUITOUS_LANGUAGE.md 或类似文档则先查看）。
- **描述行为，而非代码** —— 写 "sync 服务应用补丁失败"，不要写 "applyPatch() 在第 42 行抛异常"。
- **复现步骤必须给出** —— 如果无法确定，就问用户。
- **保持简洁** —— 开发者 30 秒内应能读完。

归档后，打印所有本地 issue 文件路径（含阻塞关系概要），并问："下一个问题，还是结束？"

### 5. 继续会话

一直持续到用户表示结束。每个 issue 彼此独立，不要批量处理。

## 工作流总览

1. 倾听 + 最多 2-3 个澄清问题（`ask_user_question`）。
2. 后台 `subagent` 探索相关代码库区域，学习领域语言（不找修复）。
3. 判断单个 issue 还是拆分。
4. 写入 `.scratch/qa/<NN>-<slug>.md`（遵循模板与 6 条通用规则）。
5. 询问继续或结束。

## 检查清单

- [ ] 最多只问了 2-3 个澄清问题，没有过度采访。
- [ ] 后台子代理用于学习领域语言（未用于找修复）。
- [ ] issue 正文未引用文件路径或行号。
- [ ] 使用项目领域语言描述行为，而非代码。
- [ ] 复现步骤完整、具体、可编号执行。
- [ ] 拆分时按依赖顺序创建，阻塞关系标注真实。
- [ ] issue 已写入本地 `.scratch/qa/` 文件，路径已告知用户。
