# Code Review（双轴评审）

对 `HEAD` 与用户提供的某个固定点之间的 diff 做双轴评审：

- **Standards** —— 这段代码是否符合本仓库文档化的编码规范？
- **Spec** —— 代码是否忠实实现了最初的 issue / PRD / 需求？

两条轴用**并行子代理**（`subagent` 工具，默认后台运行）分别评审，互不污染上下文，最后由本技能汇总两者结论。

## 触发时机

用户要求对某个分支、PR、工作区改动或自某个基线以来的改动做 code review，或说 "review since X"/"评审自 X 以来的改动" 时触发。

## 工作流

### 1. 固定评审基准点（fixed point）

无论用户给出的是 commit SHA、分支名、tag、`main`、`HEAD~5` 等，都是固定点；若用户未指定，用 `ask_user_question` 询问。

先用 `pwsh` 捕获一次 diff 命令：

```powershell
git diff <fixed-point>...HEAD        # 三个点：与 merge-base 比较
git log <fixed-point>..HEAD --oneline
```

继续前先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。坏引用或空 diff 应在此处直接失败，而不是丢进两个并行子代理里。

### 2. 定位 Spec 来源

按以下顺序寻找最初的需求来源：

1. commit message 中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——尝试用 `web_search` 或按仓库约定获取其内容（DSH 无内置 issue 跟踪器；若仓库以本地 markdown 记录，按仓库现有约定读取）。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD/需求文件。
4. 都找不到则用 `ask_user_question` 问用户 spec 在哪。若用户说没有 Spec，则 **Spec** 子代理跳过，并在最终报告中注明 "no spec available"。

### 3. 定位 Standards 来源

仓库里任何规定了代码应如何编写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。按仓库现有约定查找，不存在则跳过工厂文档，只用下面的气味基线。

在仓库自带文档之上，Standards 轴始终携带以下**气味基线**（Fowler《Refactoring》第 3 章的固定代码气味集合）。两条约束：

- **仓库规范优先。** 文档化的仓库规范始终生效；若它认可了基线本会标记的点，则抑制该气味提示。
- **始终是判断项。** 每个气味都只是带标签的启发式判断（"疑似 Feature Envy"），绝非硬性违规；与任何规范一样，凡是工具链（linter/格式化器）已强制的东西都跳过。

每条气味的读法是 *它是什么* → *怎么修*；将其与 diff 比对：

- **Mysterious Name** —— 函数/变量/类型的名字无法体现它做什么或存什么。→ 重命名；若想不出诚实的名字，说明设计也模糊。
- **Duplicated Code** —— 相同的逻辑形态在该改动中出现在多个 hunk 或多个文件里。→ 抽取公共形态，两处共同调用。
- **Feature Envy** —— 一个方法更多地在取其他对象的数据而非自己的。→ 把方法移动到它觊觎的数据上。
- **Data Clumps** —— 反复结伴出现的几个字段/参数（一个待诞生的类型）。→ 打包成一个类型，整体传递。
- **Primitive Obsession** —— 用原始类型或字符串顶替一个本该拥有自己类型的领域概念。→ 给该概念一个自己的小类型。
- **Repeated Switches** —— 同一类型的同样 `switch`/`if` 级联在改动中反复出现。→ 改用多态，或让两处共享一个映射。
- **Shotgun Surgery** —— 一个逻辑变更迫使改动散布到 diff 里的许多文件。→ 把一起变的东西收敛到一个模块。
- **Divergent Change** —— 一个文件/模块因多个互不相关的原因被修改。→ 拆分，让每个模块只为单一原因而变。
- **Speculative Generality** —— 为 Spec 并不需要的需求提前加的抽象、参数或钩子。→ 删掉它，内联回去，直到出现真实需求。
- **Message Chains** —— 长长的 `a.b().c().d()` 导航，调用方本不该依赖它。→ 把这段导航藏到第一个对象的一个方法后面。
- **Middle Man** —— 一个主要只是转发的类或函数。→ 砍掉它，直接调用真正的目标。
- **Refused Bequest** —— 子类/实现方忽略或覆盖了它继承的大部分内容。→ 去掉继承，改用组合。

### 4. 并行启动两个子代理

用 `subagent` 工具（在单条消息里发两次调用，均默认后台运行）并行启动两个子代理。

**Standards 子代理 prompt** 需包含：

- 完整的 diff 命令和 commit 列表。
- 第 3 步找到的 standards-source 文件清单，**外加第 3 步的气味基线全文**——子代理没有本会话上下文，必须自行自包含。
- 简报："按文件/hunk（如相关）汇报 (a) diff 中每一处违反文档化规范的地方：引用规范（文件 + 规则）；以及 (b) 你发现的任何基线气味：命名它并引用对应 hunk。区分硬性违规与判断项——文档化规范违约可能是硬性的，但基线气味永远是判断项，且文档化仓库规范优先于基线。跳过任何工具链已强制的点。400 字以内。"

**Spec 子代理 prompt** 需包含：

- diff 命令和 commit 列表。
- spec 的路径或抓取到的内容。
- 简报："汇报： (a) spec 要求但缺失或只实现了一部分的需求； (b) diff 里没被要求的行为（范围蔓延）； (c) 看起来实现了但实现有误的需求。每条发现引用 spec 对应行。400 字以内。"

若 spec 缺失，跳过 Spec 子代理并在最终报告中注明。

> 注意：子代理没有本会话的对话上下文，每个 prompt 都必须自包含（diff 命令、文件清单、spec 内容、气味基线等全部随 prompt 提供）。

### 5. 汇总

把两份报告分别放在 `## Standards` 和 `## Spec` 标题下，逐字或轻微清理后并列展示。**不要合并或重排两者的发现**——两条轴刻意保持独立（见下）。

最后加一行总结：每条轴各有多少发现，以及 *每条轴各自* 最差的问题（若有）。不要在两条轴之间挑一个"总冠军"——那正是本分离要防止的重新排序。

## 为什么分两条轴

一处改动可能过一条轴而挂另一条：

- 完全符合每个规范却实现了错误的东西 → **Standards 过，Spec 挂。**
- 完全按 issue 实现却破坏了项目约定 → **Spec 过，Standards 挂。**

分开汇报才能防止其中一条轴掩盖另一条。

## 工具适配

- 所有 shell 命令用 `pwsh`（PowerShell）执行。
- 交互式提问用 `ask_user_question`（一次可问多个问题）。
- 并行子代理用 `subagent`（默认后台运行；需要立即拿结果时才 `run_in_background: false`）。
- 对本地文件/报告的创建与编辑用 `write` / `edit` 工具。
- 获取在线 spec/文档用 `web_search`。
