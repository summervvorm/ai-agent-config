# 诊断 Bug

一套面向困难 Bug 的纪律。除非有明确理由，否则不要跳过任何阶段。

在探索代码库时，先读取 `CONTEXT.md`（如果存在）以建立相关模块的清晰心智模型，并检查你将要改动的区域内的 ADR 文档。

## 阶段 1 — 建立反馈回路

**这一阶段的技能就是整个技能。** 其余都是机械动作。如果你有一个针对该 Bug 的**tight（紧凑）pass/fail 信号**——能够精确命中这个 Bug 的信号——你一定能找到根因；二分、假设验证、插桩都只是消费它。如果你没有这样的信号，再怎么盯着代码看也救不了你。

在这里投入不成比例的精力。**要主动，要有创造力，绝不放弃。**

### 构造反馈回路的方法——大致按此顺序尝试

1. **失败测试**：在任何一个能触达这个 Bug 的 seam（接缝点）上编写——单元、集成、端到端。
2. **Curl / HTTP 脚本**：对着运行中的开发服务器（dev server）发起请求。
3. **CLI 调用**：用 fixture 输入调用命令行，把 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，对 DOM / console / network 做断言。
5. **重放抓取的轨迹**：把真实网络请求 / 载荷 / 事件日志保存到磁盘，在隔离情况下重放经过该代码路径。
6. **一次性测试台（throwaway harness）**：搭一个最小的系统子集（单个服务、mock 掉依赖），用单次函数调用来触发这条 Bug 代码路径。
7. **属性 / 模糊测试循环**：如果是"有时输出错误"，跑 1000 组随机输入，找出失败形态。
8. **二分回测**：如果 Bug 出现在两个已知状态（commit、数据集、版本）之间，把"在状态 X 启动 → 检查 → 重来"自动化，以便 `git bisect run`。
9. **差分循环**：同一输入分别跑旧版本 vs 新版本（或两种配置），diff 输出。
10. **HITL 循环脚本**：最后手段。如果必须由人来点，就用内联 PowerShell 模板（见文末）结构化地驱动他们，把采集到的输出回传给你。

把正确的反馈回路建好，Bug 就已经解决了 90%。

### 收紧回路

把回路当作产品来打磨。一旦有了_一个_回路，就**收紧**它：

- 能更快吗？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 信号能更尖锐吗？（断言具体症状，而不是"没崩溃"。）
- 能更确定吗？（固定时间、固定 RNG 种子、隔离文件系统、冻结网络。）

一个 30 秒的 flaky（时好时坏）回路几乎不比没有回路强；一个 2 秒的确定性回路才是 tight——那是排障的超能力。

### 非确定性 Bug

目标不是一个干净的复现，而是**更高的复现率**。把触发循环跑 100 次、并行化、增加压力、收窄时序窗口、注入 sleep。50% 概率 flake 的 Bug 可以排查；1% 的不行——持续提高复现率直到它可排查为止。

### 实在建不出回路时

停下来，明确说出来。列出你试过的所有尝试。然后向用户请求：(a) 能复现它的那个环境的访问权限，(b) 一个抓下来的产物（HAR 文件、日志 dump、core dump、带时间戳的录屏），或 (c) 允许添加临时生产插桩。**在没有回路之前，不要进入假设阶段。**

### 完成判据——一个会变红（red）的 tight 回路

阶段 1 完成的标准：回路是 **tight** 且**能变红（red-capable）**——你能说出**一条命令**（脚本路径、测试调用、或一次 curl），它**已经被你实际跑过至少一次**（贴出调用与它的输出），并且满足：

- [ ] **能变红**——它驱动真正的 Bug 代码路径，并断言**用户的确切症状**，因此它能在"该 Bug 存在"时变红、修复后变绿。不是"运行不报错"——它必须能抓到这个具体的 Bug。
- [ ] **确定性**——每次运行结果一致（flaky 情况：按上文锁定一个高的复现率）。
- [ ] **快**——秒级，而不是分钟级。
- [ ] **可无人在场运行**——你可以无人值守地运行它；需要人在循环里时，只用文末的 HITL PowerShell 模板。

如果你发现自己还没让这条命令存在就开始读代码构造理论——**停下。直接跳到假设正是这个技能要防止的失败模式。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行回路，看着它变红——Bug 出现了。

确认：

- [ ] 回路产生的是**用户描述**的失败模式——而不是碰巧在附近的另一个失败。修错 Bug = 修错补丁。
- [ ] 失败在多次运行间可复现（对非确定性 Bug，则要达到足以用来排查的高复现率）。
- [ ] 你已抓下确切症状（错误信息、错误输出、慢的耗时），供后续阶段验证修复是否真的对症。

### 最小化

一旦变红，把复现缩小到**仍然会变红的最小场景**。**一次只砍**输入、调用者、配置、数据、步骤中的一项，每次砍完重跑回路——只保留对这个失败起承重作用的东西。

为什么要做：最小复现会缩小阶段 3 的假设空间（剩下可怀疑的部件更少），并在阶段 5 变成干净的回归测试。

完成标准：**剩下的每个元素都是承重的**——去掉其中任何一个都会让回路变绿。

在没有完成"复现**且**最小化"之前，不要继续。

## 阶段 3 — 生成假设

在检验任何假设之前，先生成 **3–5 个排序后的假设**。只生成单一假设会让思维锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：说明它所做出的预测。

> 格式："如果 <X> 是根因，那么 <改变 Y> 会让 Bug 消失 / <改变 Z> 会让它更严重。"

如果你说不出预测，那这个假设只是种感觉（vibe）——丢弃它，或把它打磨锋利。

**在测试之前把排序列表展示给用户。** 用户常有领域知识能瞬间重排（"我们刚部署了第 3 项的改动"），或知道哪些假设已经被排除。这是个便宜的检查点，能省大量时间。但不必卡住它——如果用户不在场，就按你的排序继续。

## 阶段 4 — 插桩（Instrument）

每个探针必须对应阶段 3 里的一个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**（如果环境支持）。一个断点胜过十条日志。
2. 在能区分各假设的**边界**处做**定向日志**。
3. 绝不做"日志全开然后 grep"。

**给每条调试日志加唯一前缀**，例如 `[DEBUG-a4f2]`。结束时清理只需一次 grep。带标签的日志会被删，不带标签的存活。

**性能分支**：对性能回退，日志通常是错的。改为：先建立一个基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

**在修复之前写回归测试**——但前提是存在**正确的 seam**。

正确的 seam 是：测试在**调用点**处按它真实出现的方式练习那个 Bug 模式。如果唯一可用的 seam 太浅（当 Bug 需要多个调用者时却只有一个调用者的测试；无法复现触发该 Bug 的调用链的单测），在那种 seam 上写回归测试只会带来虚假的信心。

**如果不存在正确的 seam，这本身就是一条发现。** 把它记下来。是代码库架构阻止了该 Bug 被锁定。把这个标记给下一阶段。

如果存在正确的 seam：

1. 把最小化后的复现转成该 seam 上的失败测试。
2. 看它失败。
3. 应用修复。
4. 看它通过。
5. 用原始的（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6 — 清理 + 复盘

在宣布完成之前必须完成：

- [ ] 原始复现不再重现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或已记录缺失 seam 这件事）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（用 grep 该前缀确认）
- [ ] 一次性原型已删除（或移到一个明确标注的调试位置）
- [ ] 最终被证实的那个假设写在 commit / PR message 里——这样下一个调试者能学到东西

**然后问：是什么本可以阻止这个 Bug？** 如果答案涉及架构改动（没有好测试 seam、调用者纠缠不清、隐藏耦合），就把具体情况交给 improve-codebase-architecture 技能处理。在修复**落定之后**再给出建议，而不是之前——因为此刻你掌握的信息比开始时更多。

## 在 DSH 中的工具用法

- 所有编辑用 `edit` / `write` / `read` 工具；浏览文件用 `grep` / `glob`。
- 运行命令用 `pwsh`（PowerShell）。用 `start <path>` 在 Windows 上打开文件；临时目录用 `$env:TEMP`。长命令放后台跑（`run_in_background: true`），用 job id 收取输出、`job_kill` 停止。
- 按步骤管理进度用 `todo_write` 任务清单；独立探活/并行的探查可委派给 `subagent`（默认后台运行；需要立即拿结果时 `run_in_background: false`，且子代理没有本会话上下文，prompt 必须自包含）。
- 需要向用户确认或提问（如阶段 3 展示假设排序）用 `ask_user_question`（一次可问多个问题）。

## HITL 循环 PowerShell 模板

用户必须亲自操作时才用（最后手段）。把下面模板复制到一个 `.ps1` 文件，按注释编辑步骤，然后运行；模型运行脚本，用户在终端跟随提示操作，脚本末尾以键值对打印采集到的结果供模型解析。

```powershell
# 人机协同复现回路。复制此文件，按注释编辑步骤后运行。
# 两个辅助函数：
#   step "<指令>"        # 显示指令，等待回车
#   capture VAR "<问题>" # 显示问题，把用户回答读入 $VAR
# 结束时采集到的值以 KEY=VALUE 打印，供模型解析。

function step([string]$msg) {
  Write-Host "`n>>> $msg"
  Read-Host "    [完成时按回车]"
}
function capture([string]$var, [string]$question) {
  Write-Host "`n>>> $question"
  return Read-Host "    > "
}

# --- 从这里开始编辑 ------------------------------------------------

step "打开 http://localhost:3000 上的应用并登录。"

$ERRORED  = capture "ERRORED"  "点击「Export」按钮。它抛错了吗？(y/n)"
$ERROR_MSG = capture "ERROR_MSG" "粘贴错误信息（或 'none'）："

# --- 到这里结束编辑 ------------------------------------------------

Write-Host "`n--- Captured ---"
Write-Host "ERRORED=$ERRORED"
Write-Host "ERROR_MSG=$ERROR_MSG"
```

> 注（PowerShell 函数行为）：上面模板里 `capture` 返回字符串、由调用方赋给 `$ERRORED` 变量（PowerShell 不要求函数端用 `Set-Variable` 回写）。可按需把 `capture` 的返回值直接赋给任意变量。
